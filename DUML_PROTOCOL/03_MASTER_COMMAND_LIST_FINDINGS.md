# Master DUML command list — methodology and findings

Produced in response to: "go through all the firmware to create a list of
all DUML commands and all their associated sender, receiver, cmd id,
cmd set, and expected payload breakdown."

## 1. The baseline: `DUML_PROTOCOL/ALL_COMMANDS.csv`

Generated by `DUML_PROTOCOL/tools/export_master_list.py` from
`duml_py/duml/commands.json` — **877 commands across 16 non-empty cmd_sets**
(157 with a full byte-level payload breakdown; the rest are known by name/
cmd_id and sendable/receivable as raw bytes, per the existing README).

This *is* already "all the firmware" in one specific sense: `commands.json`
was itself built from the public `dji-firmware-tools` Wireshark Lua
dissector (`dji-dumlv1-*.lua`), which is the accumulated product of the
`dji-rev`/"Original Gangsters" community's firmware RE across essentially
every DJI product line since ~2016 (Phantom 3, A3, Inspire 1/2, Matrice
100/600, Mavic Pro/2/3, Spark, Osmo, Agras, ADS-B module, RTK, etc.) — it's
the superset the whole community has assembled, not a single-firmware
snapshot.

**Sender/receiver caveat (important, not a gap to "fix"):** DUML's
sender_type/receiver_type are *frame-level* fields (bytes 4-5 of every
frame — see `00_FRAME_FORMAT.md`), not fixed metadata of a command
definition. A Response frame simply has sender/receiver swapped relative
to the Request that triggered it, and the real sender of a Request is
whichever host issued it (APP, PC/DJI Assistant, or RC relaying one of
those) — that's not recoverable from the command's definition alone, only
from an actual captured frame. The CSV's `typical_receiver` column is
`CMD_SET_TYPICAL_RECEIVER` from `duml/enums.py` (which chip normally
handles that cmd_set) and `typical_request_sender` is this session's own
best-effort inference by what each cmd_set's commands *do*, clearly
labeled as such — not firmware-derived fact. Treat both as "typical", not
guaranteed per command.

## 2. Confirmed real gaps in the public dissector itself

Checked `DUML_PROTOCOL/tools/duml_lua_db.json` (the parsed Lua source,
the earlier-stage input commands.json itself is built from) directly:

- `cmd_set` **0x0c (ESC)**: table name `ESC_UART_CMD_TEXT` exists in the
  dissector source but is **literally empty** (`{}`) — zero commands
  defined anywhere upstream. Plausible explanation, consistent with this
  repo's own `01_BINARY_ANALYSIS_FINDINGS.md` (§1): ESC modules are often
  addressed indirectly through the Center Board's translation layer rather
  than with their own first-class cmd_set traffic on the main bus.
- `cmd_set` **0x10 (Automation)**: table name `AUTO_UART_CMD_TEXT` also
  exists and is also **completely empty**. No public source checked this
  session documents DJI's waypoint/mission-automation command set at all.

Both are therefore real, acknowledged-upstream gaps — not something
missing from this repo's extraction.

## 3. Extending coverage: freshly decrypted firmware, this session

To "use whatever firmware has public decryption supported" rather than
rely only on the pre-existing dissector, pulled and decrypted three
additional, independent firmware packages this session, using the
*fully public* legacy "xv4" container format (`dji_xv4_fwcon.py` —
no uncertain/unpublished keys involved, unlike the IMAH-era WM265e wall
hit earlier):

| Product | Package | Host |
|---|---|---|
| A3 (standalone flight controller) | `A3_FW_V01.06.00.10.bin` | `s3-ap-northeast-1.amazonaws.com` (dji-firmware-tools' own public test mirror) |
| Matrice 600 Pro | `MATRICE600PRO_FW_V01.00.00.80.bin` | same |
| Inspire 1 (WM610/FC550) | `WM610_FC550_FW_V01.08.00.92.bin` | same |

All three extracted cleanly; `file` recognizes the flight-controller
modules as genuine ARM Cortex-M firmware with legible vector tables
(entropy ~7.05/8, consistent with real code, not still-encrypted garbage).
M600 Pro's package additionally yielded 6 near-identical ~22 KB modules
(`m1100`-`m1106`) — very plausibly its 6 rotor ESCs (M600 is a hexacopter)
— the single most promising concrete target for the cmd_set 0x0c gap.

A parallel mining pass (5 agents, one per binary: A3 FC, M600 Pro FC,
M600 Pro ESC `m1100`, Inspire 1 FC, Inspire 1 `m0400`) was launched to
search each for the DUML CRC8 table signature (confirming the protocol is
present at all), and for any command-name/parameter strings or dispatch
evidence not already in `commands.json`.

## 4. What "go through all the firmware" realistically can't mean here

For completeness: the *current-generation* IMAH-signed firmware for
WM265e/WM265t (Mavic 3 Enterprise/Thermal) remains undecryptable with any
publicly known key, per `02_WM265_MAVIC3_NFZ_FINDINGS.md` — so it
contributes nothing to this command list beyond what's already in
`commands.json`. Going further than what's above (e.g. the full current
Mini/Air/Avata/O4 generation) would need either a fresh public key leak
this session didn't find, or physically sniffing live traffic off a real
aircraft (the `watch_nfz_unlock.py` approach, generalized to every cmd_set)
— which needs real hardware, not more firmware downloads.
